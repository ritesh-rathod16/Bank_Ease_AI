# Security and privacy status

## Implemented in the local prototype

### Sensitive document handling

KYC extraction is limited to explicitly labeled full name, birth date, and address text. Government identity numbers and standalone identity cards are not classified or extracted. KYC page text and fields are not returned by global search or the document assistant; source previews and field details remain restricted to the authenticated document owner. Extraction is not identity or authenticity verification.

- The development API runner binds to loopback by default; the Next.js UI proxies its API paths same-origin.
- Registration enforces verified email before login. Passwords use Argon2id; unknown-user login performs a dummy password verification.
- Opaque session tokens and email/reset tokens are stored as SHA-256 hashes. Sessions expire after 12 hours and use HttpOnly, SameSite cookies; the Secure flag is enabled when `APP_ENV=production`.
- Mutations require a CSRF header matching the readable CSRF cookie; authenticated session CSRF values are bound to the stored session hash.
- Login/registration/recovery attempts have a process-local per-IP limit and generic login/recovery messages.
- Document IDs are random; every document endpoint and the document list query uses the authenticated owner ID. Cross-account document access returns 404.
- Account workflows include password reset/change, session revocation, data export and account deletion. Document removal also removes extracted page records.
- Loan term corrections require an authenticated owner session and CSRF protection. They preserve extracted source values/evidence, record actor/time/reason in an append-only per-field history, and are removed with the owning document.
- Statement-row corrections require owner scope, CSRF protection, and an expected revision. Imported normalized values, source cells, and PDF evidence are immutable; effective values and append-only correction history are stored separately and included in the owner's data export. Staff roles do not grant access to another customer's statement rows. A reviewer receives transaction evidence only through an explicitly assigned task snapshot; review decisions do not change transaction values.
- Saved comparisons are private owner records. Reopen, report, export, delete, document-delete cascade, and account-delete cascade all filter by owner; both source documents are rechecked before a result is returned. Result snapshots retain excerpts of extracted evidence, so they are deleted with either source document and included in the caller's data export.
- Accounts default to the customer role. The system administrator role comes only from the server-side `BANKEASE_ADMIN_EMAILS` allowlist; requests cannot self-assign it. Configured administrators can provision non-admin staff roles and assign review tasks. Assigned reviewers can read only the task snapshot explicitly assigned to their account; managers do not receive general customer-document access. Review and role-change events are recorded without copying document passage text into the audit log.
- Customer-requested review snapshots are owner/document scoped, returned with evidence only to the owner and assigned reviewer, and deleted with the document or account. Role revocation unassigns pending work; account deletion removes owned review tasks and audit events and unassigns tasks assigned to the deleted account.
- Scanned-page OCR runs in a subprocess; bounded PDF bytes (including temporary in-memory PDFs converted from source images) are passed over stdin, each page has a timeout, total OCR pages and duration are capped, pages have image-dimension limits, each response is capped at 4 MB, and a document is capped at 50,000 OCR words. OCR requires a separately installed Tesseract engine and language data. OCR-derived fields and statement rows are marked for human review; OCR text is not treated as verified data.
  - Uploads enforce a byte limit and actual PDF/image signatures or OpenXML container validation for DOCX/XLSX. PDF/image page dimensions are bounded before OCR; DOCX archive entries, expanded size, XML part size, extracted characters, sections, and section length are capped. DOCX relationships are not followed; macro-enabled and embedded OLE documents are rejected. XLSX expanded size, XML part size, worksheet count, columns, rows, and cell lengths are capped. Macro-enabled and externally linked workbooks are rejected, and formulas are never executed. Accepted originals use generated names in private local storage, are never placed under the frontend, and are served only after an owner-scoped lookup. Responses disable caching and MIME sniffing; office files download as attachments.
- Background processing jobs contain owner/document IDs and operational status only; no uploaded bytes or extracted passages are copied into the queue. A worker rechecks ownership before reading the private source, renews a bounded lease, and checks that its lease remains active before and after committing results. Status and retry endpoints require the owner's session; retry mutations also require CSRF. Document/account deletion removes queued jobs, and startup recovery recreates a missing queued record for a saved `processing` document.
- The document worker performs bounded retention sweeps using the configured creation-time cutoff. Each sweep cancels document jobs before deleting the source and linked document, comparison, conversation, message, review-task, and task-audit records. Uploads also run a sweep for that owner. `BANKEASE_RETENTION_HOURS=0` disables expiry; scheduled sweeps require the document worker to be enabled. Local JSON behavior is tested; MongoDB behavior has not been exercised against a live server.
- The local JSON queue uses a process-local lock and is supported only with a single API process. MongoDB claims use atomic document updates and leases, but multi-process behavior has not been verified against a live MongoDB deployment.
- Assistant conversations may reference up to five selected owner-authorized documents. Message reads, sends, and deletion filter by conversation owner; each send rechecks access to every source before retrieving page or transaction-row evidence. Cited message text is included only in that owner's export and is deleted with the conversation, document, or account.
- Account archive export uses the authenticated owner scope, generated archive entry paths, a manifest, and a 100 MB uncompressed size cap. The response is non-cacheable and does not include local filesystem paths.
- Local source files and records are not encrypted at rest. POSIX source/record files use mode `0600` and upload directories use `0700`; Windows ACL behavior has not been independently verified. The prototype is not suitable for real customer financial documents.

## Limitations

This prototype is not ready for public deployment or real customer records. Local JSON analysis, extracted text, and original files are not encrypted at rest; Windows ACL behavior is not explicitly configured or verified. Auth JSON files request restrictive permissions on POSIX, but local storage is not a production repository. The rate limiter is process-local and does not work across replicas. Email delivery, encrypted local storage, host ACLs, backup-retention deletion, production secrets, TLS termination, operational monitoring, and live Mongo operations have not been verified. Review supports owner-requested loan-field and statement-row evidence checks, but not task due dates, branch-scoped access, or multi-step approval policies. Production startup is blocked until the deployment gate is satisfied.

Development email verification/reset tokens are displayed as loopback links only. Do not expose development link mode to a public service. No email provider is configured.

## Before public deployment

Use a durable shared rate limiter, production email delivery, encrypted private storage with lifecycle and deletion controls, TLS and secure secrets, redacted logs, readiness/health monitoring, verified backup/restore and migration procedures, resource/time limits, and security testing. Review the applicable privacy and financial-sector requirements for the product and deployment. This repository makes no legal compliance claim.
