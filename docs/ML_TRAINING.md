# ML and data development status

## Current approach

The product baseline remains deterministic: PyMuPDF text extraction, regex-based loan-term extraction, rule-based clause tagging, BM25-style evidence retrieval, and exact-formula EMI calculations. A research-only GPT-2 LoRA classifier has now been fine-tuned on synthetic documents, but it is not integrated into product inference because its held-out result did not beat the deterministic classifier. There is no production model, embedding index, or experiment registry. Optional Tesseract OCR is a separate extraction path, not a trained BankEase model.

## Reproducible synthetic corpora

Prepare the original fictional regression PDFs with:

```powershell
python scripts/prepare_ml_dataset.py --output data/runtime/ml/synthetic-v1
```

That corpus has 20 accepted PDFs and 140 field labels over three existing template families. Its whole-family split puts 17 loan agreements in train, 2 sanction letters in validation, and 1 repayment schedule in test. It lacks class coverage and is not a suitable held-out benchmark.

Generate the small three-family corpus for a split/evaluator smoke check:

```powershell
python scripts/make_layout_variants.py
python scripts/prepare_ml_dataset.py --manifest data/runtime/ml/layout-variants-v1/manifest.json --output data/runtime/ml/layout-variants-v1/prepared
python scripts/evaluate_synthetic_baseline.py --manifest data/runtime/ml/layout-variants-v1/manifest.json --split test --output data/runtime/ml/layout-variants-v1/test-evaluation.json
```

This produces 9 PDFs and 63 field labels. Each split holds out one entire family and includes all three document types (3 PDFs and 21 field labels per split). The deterministic rules matched the construction-derived document type/category and field value/status/page/evidence on this tiny test split. It is only a generator and evaluator check.

## Experimental classifier fine-tuning

The larger synthetic experiment uses 67 parameterized variants (201 PDFs, 1,407 field labels) and groups each three-document variant into exactly one split. The current prepared split has 141 train, 30 validation, and 30 test documents; each partition includes 10 test/validation or 47 train documents per class. The generator reuses only three base layout styles across all partitions, so the test is a held-out generated-variant check, not a holdout of unseen document layouts or independent banking sources. This clears the size and class-coverage checks, but its labels are generated by construction and have not been human reviewed. The normal training gate rejects it. An explicit `--allow-synthetic-research` flag permits a research-only run and records `production_ready: false` in the report and model card.

Install the optional pinned training stack in an isolated environment, then run:

```powershell
python -m pip install -r requirements.txt -r requirements-ml.txt
python scripts/make_layout_variants.py --family-count 67 --output data/runtime/ml/gpt2-classifier-v1
python scripts/prepare_ml_dataset.py --manifest data/runtime/ml/gpt2-classifier-v1/manifest.json --output data/runtime/ml/gpt2-classifier-v1/prepared
python scripts/train_document_classifier.py --allow-synthetic-research --output data/runtime/ml/gpt2-classifier-v1/model-best --report data/runtime/ml/gpt2-classifier-v1/experiment-best.json
```

`requirements-ml.txt` pins PyTorch, Transformers, PEFT, and Hugging Face Hub separately from API requirements. The script requires the base model to be already present in the local Hugging Face cache and loads it with network access disabled. It verifies manifest hashes, generated-file hashes, synthetic provenance, class coverage, split sizes, and that entire source families stay in one partition. GPT-2 receives a sequence-classification head and LoRA adapters over attention/projection modules. The output adapter, model card, validation history, held-out metrics, artifact checksums, and rule-baseline comparison are written below `data/runtime/ml/gpt2-classifier-v1/`; these are ignored runtime artifacts.

The completed CPU experiment used the local [`openai-community/gpt2` checkpoint](https://huggingface.co/openai-community/gpt2) (MIT license shown on its model card), revision `607a30d783dfa663caf39e06633721c8d4cfcd7e`, three epochs, LoRA rank 4, and a seed of 2026. It used Python 3.14.2, PyTorch 2.14.1, Transformers 5.20.2, and PEFT 0.21.2. The best validation checkpoint was epoch 2. On the 30-document held-out generated-variant split, that checkpoint scored **14/30 (46.7%)** document-type accuracy and **43.5% macro F1**; existing deterministic title rules scored **30/30 (100%)** on the same generated documents. The test set reuses the same three base layout styles as training, so this is not an unseen-layout result. All labels are synthetic, there are only 10 examples per type in test, and every document comes from one generator. Keep the adapter out of product inference. The result is a pipeline demonstration and a negative model-selection result, not a product-quality model.

Both corpora are generated runtime artifacts. The preparation script verifies generator identity, synthetic markers, file-path containment, PDF signatures, page counts, and checksums before extracting selectable text with PyMuPDF. It writes deterministic `documents.jsonl`, `fields.jsonl`, and `split_manifest.json` files. Field labels preserve raw and normalized values, status, page, matching source-line evidence, and exact text offsets only when valid. Output records file and generator provenance.

## Deterministic regression evaluator

Run:

```powershell
python scripts/evaluate_synthetic_baseline.py --output data/runtime/ml/synthetic-baseline-evaluation.json
```

It evaluates the existing document classification and field extraction rules against generator-derived labels. It validates the corpus first, records the manifest hash, reports value/status/page/evidence checks and error examples, and explicitly excludes the partially unreadable fixture from selectable-text field evaluation. It does not train or modify a model. Its results are a regression signal over known templates only; they are not held-out, production, or real-world accuracy estimates.

For any adopted source, record the exact version, source URL, acquisition date, license text and scope, permitted use, schema, preprocessing, split lineage, privacy review, and known limitations. Do not treat a code repository license or a third-party mirror label as automatically covering source documents or derived media. Use only a documented, permitted subset.

## Production training gate and next benchmark

Do not train a production candidate until there are multiple independently sourced document families per target class, human-reviewed gold labels, source-level train/validation/test separation, confirmed rights, and an untouched representative test set. Add controlled layout and OCR variation plus missing, ambiguous, conflicting, duplicate, and arithmetic-error cases. Keep customer files, extracted records, and corrections out of training by default. The experimental override exists only to prove the training/evaluation pipeline and must not change this production gate.

The currently prepared evidence-chat corpus does **not** satisfy this gate: it is generator-derived, not human-reviewed, and its manifest sets `training_approved=false`. The current trainer accepts only that synthetic corpus format and always records `production_ready=false`; do not change those flags to force a product run. FinQA is also excluded until source-report rights are reviewed. A production corpus needs its own reviewed manifest and a reviewed gold evaluation set before the trainer can accept it.

Before model selection, compare rule-based and suitable pretrained baselines on field exact match, numeric normalization, status, evidence/page correctness, table structure, discrepancy precision/recall, citation support, abstention, OCR robustness, latency, and resource use. Group splits by document family/source to prevent leakage. Store configurations, seeds, dependency versions, artifacts, evaluation reports, and model cards when a real training run exists. Never record fabricated metrics or training results.

## Synthetic evidence-chat fine-tuning experiment (2026-10-30)

The application has a working local Ollama chat model, Qwen3 4B Instruct. A separate training experiment uses the smaller [Qwen3-0.6B model](https://huggingface.co/Qwen/Qwen3-0.6B), whose official model card declares Apache-2.0. The exact Hugging Face revision is `c1899de289a04d12100db370d81485cdf75e47ca`; its files are cached under ignored `data/runtime/hf-cache`. This is a causal chat model and is separate from the GPT-2 document classifier and Ollama's quantized inference model.

`scripts/prepare_chat_sft_dataset.py` converts only the generated fictional PDF corpus into evidence-cited question-answering and abstention examples. The current family-disjoint corpus has **1,269 train, 270 validation, and 270 test examples** across 47/10/10 source families. It contains no customer data, is not human reviewed, and is explicitly unapproved for product training. It asks about supported synthetic financial fields and includes missing-field abstentions; it does not establish general knowledge or real-document performance.

Prepare the data and run a deliberately limited tooling smoke test with the local cached model:

```powershell
python scripts/prepare_chat_sft_dataset.py --output data/runtime/ml/chat-evidence-sft-v3
python scripts/train_chat_adapter.py --allow-synthetic-research --dataset data/runtime/ml/chat-evidence-sft-v3 --output data/runtime/ml/qwen3-0.6b-evidence-lora-v1 --epochs 1 --max-length 384 --batch-size 1 --seed 2026
```

The runner uses LoRA on Qwen3 attention projections, disables network access during model loading, verifies dataset file hashes and family-disjoint splits, and writes an adapter, model card, and experiment report. The exact `--max-length 384` is included because the recorded run used that context limit. The report always marks the result `production_ready=false`; the default full run is not a viable training plan for this CPU-only development machine and should be attempted only after checking available RAM/time. Use `--max-examples-per-split` and `--max-train-steps` only for a smoke run; such a report sets `smoke_limited_run=true` and is not a training quality result. No adapter produced by this synthetic corpus may be selected for customer inference without human review and a representative, rights-cleared benchmark.

The current host has no NVIDIA GPU and reports AVX2 CPU support. A BF16 one-step smoke was stopped after over eight CPU minutes without finishing its first optimizer step. The CPU runner now selects FP32 to use the host's optimized CPU kernels. The one-step FP32 smoke completed with training loss 0.6833 and one-example validation loss 0.8037; held-out generation was disabled. A 32-step FP32 run completed in 243 seconds and saved a smoke-limited adapter at `data/runtime/ml/qwen3-0.6b-evidence-lora-32step-research`. It used 32 randomly sampled examples for each partition, one optimizer step per training example, and two held-out generation examples limited to 16 new tokens. The tiny generation check contained the expected field value in 2/2 answers and the expected page citation in 1/2. This is not a quality result: the examples and labels are synthetic and unreviewed, the test has only two generations, and the run is marked `production_ready=false` and `training_approved=false`. Full 0.6B fine-tuning on CPU remains resource constrained.

## Conversational model registry and limitations (2026-10-30)

`config/ai_models.json` records model task, base model, version, artifact format/path, license, and evaluation status. The GPT-2 artifact is labeled `document_classification`, `peft-lora-sequence-classification`, and experimental; it is not suitable for general chat or document explanation. Ollama and Qwen3 4B local conversational inference have been verified. The Qwen3-0.6B base checkpoint and synthetic chat SFT pipeline are present, but the resulting adapter is not production-ready or registered for inference. FinQA remains `training_approved=false` pending source-report rights review and task suitability.

For a compatible fine-tuned conversational model, create/import and evaluate it as an Ollama model first, then register the installed tag:

```powershell
python scripts/register_ai_model.py --name bankease-chat-v1 --ollama-model bankease-chat:latest --base-model qwen3:4b-instruct --version 1 --format ollama-gguf --license "actual license" --evaluation-status not_evaluated
```

The registration helper verifies the installed Ollama tag and writes metadata. It does not convert adapters, train, or certify model quality. The Qwen3-0.6B Transformers adapter is not directly served by the current Ollama router. See `AI_ENGINE_ARCHITECTURE.md`, `AI_EVALUATION.md`, and `ML_DATASETS.md` before an approved training run.
